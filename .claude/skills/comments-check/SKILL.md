## 代码注释质量检查

对代码文件进行全面检查，确保注释达到"小白也能看懂"的标准。支持 Python (FastAPI/LangChain) 和 TypeScript (React) 两种语言。

---

## 三大检查维度

### 维度 1：注释覆盖率

**目标：每 10 行代码中，至少 3 行是注释（30% 注释率）**

检查规则：
- 每个 `function` / `export function` / `async def` **必须**有 docstring/JSDoc 或行前注释
- Python: 每个类和模块顶部应有 docstring
- TypeScript: 每个 `const` / `let` 定义的**核心变量**应有简短注释
- 复杂表达式或算法（3 行以上）必须有注释解释

计算方法：
```
注释率 = 注释行数 / 总行数 × 100%
```
- Python注释：`#`、`"""` (docstring)
- TypeScript注释：`//`、`/* */`、`/** */` (JSDoc)
- 空白行不计数
- 目标：>= 30%

### 维度 2：注释内容准确性

**目标：注释说的和代码做的必须一致**

检查规则：
- 对照注释和实际代码逻辑，看是否匹配
- 如果改了代码逻辑但注释没更新 → 标记为"过期注释"
- 注释中的参数名、返回类型要和代码一致

常见错误示例：
```python
# ❌ 注释和代码不匹配
def calc_total(transactions):
    """计算本月总支出"""
    return sum(t.amount for t in transactions if t.type == 'income')  # 实际只取收入！
```

### 维度 3：小白可读性

**目标：让技术小白也能通过注释理解代码在做什么**

检查规则：
- 注释是否用**大白话**而不是术语堆砌
- 复杂概念是否用了**类比**来解释
- Python docstring 的前 1-2 句应该一句话说清"这个函数干了什么"

好的注释示例：
```python
def embed_query(self, text: str) -> List[float]:
    """
    把用户的问题（文本）转换成数字向量
    就像把中文翻译成机器能理解的"坐标"，
    不同问题如果语义相似，它们的"坐标"也会很接近
    
    :param text: 用户输入的问题文本，比如"这件衣服有什么尺码？"
    :return: 1024维的浮点数向量
    """
```

## 执行流程

### 步骤 1：确定检查目标

- 用户指定了文件 → 直接检查该文件
- 用户没有指定 → 检查最近修改的文件
- 优先检查 `backend/app/` 和 `frontend/src/`

### 步骤 2：逐维度分析

读取目标文件，对每个函数/核心代码段进行三维度评分：

| 分数 | 覆盖率 | 准确性 | 小白可读性 |
|------|--------|--------|-----------|
| ⭐⭐⭐ | >=30% | 完全匹配 | 大白话 + 类比 |
| ⭐⭐ | 15-29% | 基本正确 | 有解释但偏专业 |
| ⭐ | <15% | 有过期/错误 | 纯术语 |

### 步骤 3：输出检查报告

```
========== 注释质量检查报告 ==========

📁 检查文件：backend/app/rag/chain.py
📏 总行数：117 行
💬 注释行：XX 行
📊 注释率：XX%

====================================
综合评分：⭐⭐ / ⭐⭐⭐
====================================

———— 维度 1：覆盖率 —————
[列出缺少注释的函数/代码段]

———— 维度 2：准确性 —————
[列出注释与代码不匹配的地方]

———— 维度 3：小白可读性 —————
[列出难懂的注释，并给出改进建议]

====================================
```

---

## 重要原则

- 检查时不要修改代码，只出报告
- 给出**具体的改进建议**，而不是只说"注释不够"
- 对每个问题给出**修改后的注释示例**
- 如果注释已经很好，也要**表扬**
