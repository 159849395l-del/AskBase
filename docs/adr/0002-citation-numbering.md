# 0002. 来源编号由本站统一编排，外部服务的编号不被信任

日期：2026-09-12

## 状态

已接受

## 背景

回答里的 [N] 曾经有三套互不相干的编号同时在跑：

- 知识库上下文注入的是 [来源N: 文件名]，编号从 1 起；
- Exa Answer 返回的答案正文自带 [1][2]，指的是它自己的 citations 列表；
- 百度 / Bing 回退路径把结果整理成 [N] 标题 + 链接，编号同样从 1 起。

三者一混，用户看到的就是「正文标了 5 个来源，面板上一个都对不上」，
面板里的「来源1」甚至可能指向另一条完全无关的知识库片段 —— 面板会主动误导人。

根因不只是显示问题：来源列表里当时**根本没有网页来源**，
工具结果只被拼回消息历史，从不产出结构化来源。

## 决策

1. **网页来源是一等来源**。联网搜索的每条结果都以结构化形式（标题 + 链接 + 摘要）
   进入与知识库来源同一份列表，前端按 kind 分支渲染，网页来源必须可点击。
2. **编号只有一个来源：列表中的位置**。正文里的 [来源N] 与面板里的「来源N」
   都指来源列表的第 N 条（下标 N-1），没有第二套编号。
3. **改写发生在工具结果进入模型之前**。工具处理函数只知道自己那几条来源
   （文本里的 [N] 指它自己返回的来源列表的第 N 条），执行器知道「已经有多少条来源」，
   由它统一改写成全局 [来源N]；外部服务（Exa）自带的 [N] 在同一个环节被改掉。
   改写的判定是「编号落在 1..本次来源条数内」，越界的方括号数字（年份、序号、
   外部引用超出条数的情况）一律不动 —— 宁可不改，也不要把不是引用的数字改坏。
   代价是网页正文里恰好写成 [1]~[N] 的脚注也会被一并改写，接受这个取舍。
4. **拿不到结构化来源的工具不产生来源条目**。MCP 工具由外部服务返回纯文本，
   它内部若自带编号，本站既无从对齐、也无从改写 —— 宁可不给来源，也不给假来源。
   这也是「只有 [来源N] 可信」这条规则必须写进提示词的原因。
5. **编号顺序固定为「知识库先、网页后」**。知识库上下文在工具调用之前就已构造，
   网页来源无法插到前面；接受这个顺序，而不是假装能重排。

## 影响

- 处理函数的返回值从「只返回文本」放宽为「文本 + 可选来源」，旧的纯文本形态保持兼容。
- 上下文里 SQL 来源与文档来源的编号会接着彼此往下排，同一份上下文不再出现两个「来源1」。
- 回答里的编号可以跨轮次、跨工具累加，模型必须原样引用，不能另起编号。
- 工具调用过程随助手消息落库，否则「回答为什么引用了网页」在历史会话里无从追溯。
